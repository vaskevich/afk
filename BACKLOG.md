What was looked at and found sound, so the absence of an item is a judgement: the 22-character base62 id (~131 bits) is validated at the edge with a bounded negative cache, so enumeration and storage-read amplification on unknown ids are closed; the write token is separate, never in a URL, a log line, or the dashboard, and the QR endpoint that renders the share link sits behind it; the deployed headers match the source (`no-referrer`, HSTS, COOP/CORP, `nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`), so a share link is not leaked by Referer and cannot be framed; the dashboard renders every server string through React with no `innerHTML`, and `connect-src 'self'` contains a compromised web dependency; the client executes nothing a server sends (the only `sh` path is the user's own `curl | sh`), follows no redirects, refuses a downgrade from https in the installer, and keeps `~/.afk` at 077; a self-hoster's client references only the origin it was installed from, so a compromised `afk.osv.im` does not reach it; the container runs node as a non-root PID 1 with a digest-pinned base image, deploys go through OIDC with a role scoped to the Lightsail actions it needs and no long-lived AWS keys, and pnpm 10 runs no install scripts; the Lightsail bucket key cannot be scoped narrower than the bucket, so the documented rotation is the right control and the token-hashing item above is what shrinks its blast radius; the `!==` token comparison is not exploitable at 256 bits through a load balancer but is retired by that same item; and gzip on JSON responses is safe because no response that carries a secret reflects attacker-controlled input.

## Deployment

Decision (Sep 2026): deploy as a Lightsail container service rather than an instance.
No persistent volume, so storage is the Lightsail bucket above; TLS and the public
endpoint come from Lightsail; deploys are push-image + new deployment.

- [x] Rework `infra/` for a container service: service + custom domain certificate + DNS validation records + `afk.osv.im` record in the osv.im zone + Lightsail bucket; drop the instance, key pair, static IP, and cloud-init bootstrap. Bucket access is env vars, not Lightsail "resource access" -- see the decision log entry below.
- [x] Dockerfile that builds the dashboard and runs the server
- [x] Compile `packages/server` to plain JS instead of running it through `tsx` in the container -- `pnpm build` runs `tsc` for `@afk/shared` and `@afk/server` (`tsconfig.build.json` in each, `rewriteRelativeImportExtensions` for the `.ts` imports), the image's CMD is `node --conditions=afk-compiled packages/server/dist/index.js` (the condition is how shared's `exports` map points the compiled server at `packages/shared/dist` while every dev tool keeps resolving the TypeScript source), `tsx` is a devDependency again, and `ci.yml` starts the compiled server and curls `/api/health` so the entrypoint is exercised on Linux. Sizing: with no TypeScript transform at startup the server idles at about 86 MB RSS instead of 108 MB under `tsx` (Node 20, macOS), so the `nano` node (512 MB) `infra/` provisions has room to spare for the frame cache
- [x] `deploy.sh` becomes build image, push to Lightsail, create deployment; refactored to take bucket config from the environment (falling back to `tofu output`) and the image tag from an argument/env, so both a laptop and CI run the exact same script
